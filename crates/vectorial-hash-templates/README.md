# vectorial-hash-templates

Precomputed polygon-vs-grid intersection templates for [`vectorial-hash`](../vectorial-hash). Port of the original PHP project `multiDimensionalIndexTemplateCreation`.

## What it does

Given a list of polygons, scales, rotation angles, and grid sizes, it enumerates every combination, classifies each cell of the affected grid region as `OUT` / `MAYBE` / `IN` relative to the transformed polygon, and stores unique templates (deduplicating via the 8 rotation/flip symmetries).

The resulting set is what an evolved quadtree/octree culling step consumes at runtime.

## Pending design notes

(Working notes to fold into the documentation and, eventually, the publication PDF.)

- **Template selection at query time** (per the paper): the figure stays at its real position; for each map-cell size touched by its bounding box, pick the template whose generation offset (x, y) matches the figure origin's displacement within the global virtual grid of that cell size, so template cells align 1:1 with the static lattice. Index hierarchy: shape type → shape dimensions → cell width → cell height → angle → offset x → offset y. Shape dimensions are the minimal parameter vector per shape (circle: 1, square: 1, rectangle: 2, drop: 2 — or 1 if its proportions are fixed).
- **Index deduplication**: many (shape, dims, cell size, angle, offset) combinations produce the *same* template (same cols × rows, same cell states). The index therefore maps many keys to one shared template instance; only unique templates are stored.
- **Per-execution template cache**: during one application ("match") of a figure, several map sections share the same cell dimensions and therefore the same selected template — resolve once per (cell_w, cell_h) and reuse for the rest of that execution.
- **1×1 templates for the point test**: also generate templates with 1×1 cells (with integer origins the sub-cell offset is always (0,0), so only one per angle). When a cell has no usable template and items must be tested individually, the per-point test becomes a raster lookup instead of geometry; only `Maybe` (boundary) pixels need the exact geometric test.
- **Adaptive offset granularity (to evaluate)**: offsets are enumerated at 1-unit steps for now (option 1). A coarser step for large cells would trade precision for far fewer templates; needs a precision/cost analysis before adopting.
- **Granularity as fallback / size equivalences (to design)**: a template set for small cells can stand in for a missing larger-cell set — e.g. a 16×16-cell set at a given angle can reproduce the results of a 96×96 set at 4× granularity by aggregating blocks of small cells (all-In → In, all-Out → Out, otherwise Maybe). Related: when no template set exists for a queried cell size, consider selecting the next size *up* with a special treatment. Until designed, cells without a matching template fall back to per-item point tests, pre-filtered by the figure's bounding box.

## Hash compatibility note

`matrix::bin_code` intentionally replicates a quirk of the PHP encoder: trailing bits are **not** flushed when the cell count isn't divisible by 4. This is preserved so hashes line up with templates generated by the original PHP pipeline.

`adapter::decode_binary` is the inverse of `bin_code` and inherits the limitation: trailing cells in the PHP-bug zone are filled with `OUT`. For lossless round-trip, build the runtime grid directly from the in-memory `Matrix` via `matrix_to_template_grid` (skip the binary stage).
